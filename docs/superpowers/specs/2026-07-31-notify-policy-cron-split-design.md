# 알림 정책 전환 + cron 2분할 재편 + 성공 검증 강화

**Version:** 1.1 (2026-08-01)

## Changelog
- 1.0: 초안(2026-07-31)
- 1.1: 정찰 R3·R4 결과 반영(2026-08-01). 모듈 1 성립 확정, `start` 출처를 상세 `dd.date`로 확정, 마감선을 "공지 종료시각 + 1시간 30분"으로 수정(세미나 길이 실측 최대 90분).

## 1. 배경

현재 자동화는 성공·실패를 가리지 않고 매 실행마다 텔레그램 요약을 보낸다. 하루 15회(daily 1 + seminar 14) 알림이 오고, 그중 대부분이 "정상"이라 사용자가 읽지 않게 됐다. 읽지 않는 알림은 알림이 아니다.

무알림 전환의 전제는 **성공 판정이 믿을 만하다는 것**이다. 그런데 현재 코드는 여러 곳에서 "예외가 안 났다" 또는 "찾던 게 없다"를 성공으로 쓴다:

- `seminar_survey.run_survey()` — 제출 후 문항이 안 읽히면 `success`([seminar_survey.py:340](../../../scripts/seminar_survey.py)), 창이 닫히면 `success`([seminar_survey.py:376](../../../scripts/seminar_survey.py)). 완료 화면을 확인하지 않는다. 세션 만료·렌더링 지연도 성공이 되고, 그대로 `survey_done`에 기록돼 재시도가 영구 차단된다.
- `hmp._run_comment()` — 과거에 고정 게시물의 옛 댓글을 완료 신호로 읽어 **매일 `already_done`을 보고하면서 실제로는 한 건도 작성하지 않았다**(2026-07-29 발견).
- `keymedi` 출석 — 달력의 과거 "출석완료" 버튼을 오늘 것으로 오인하는 오판이 4회 반복됐다.

무알림으로 전환하면 이 유형의 침묵 실패는 **영구히 감지되지 않는다.** 따라서 알림 억제와 성공 검증 강화는 분리할 수 없는 한 세트다.

동시에 실행 스케줄을 재편한다. 현재는 daily 1회(15:00 예정) + seminar 14회가 서로 다른 트리거를 쓰고, 모듈 배치가 시간 특성과 어긋나 있다(세미나 신청이 하루 1회라 당일 개설·당일 방송 세미나를 놓친다).

## 2. 목표와 비목표

### 목표
1. 정상 동작 시 텔레그램을 보내지 않는다. 사람이 개입해야 할 때와 고장났을 때만 보낸다.
2. 모든 모듈이 성공을 **양성 증거**로 판정한다. 증거 없는 성공은 `unverified`로 강등해 알린다.
3. 시간 특성에 맞게 모듈을 두 블록으로 재배치한다.
4. 세미나 입장 이력에 제목·시작시각을 남겨, 설문 알림에 세미나 이름을 쓰고 마감을 판정한다.
5. 첫 1달은 전량 알림으로 운영하고, 코드 수정 없이 약알림으로 전환한다.
6. 계정 추가 시 코드 수정 없이 `credentials.json`(secret)만 고치면 되게 한다.

### 비목표
- 알림 채널 추가(이메일·Slack 등). 텔레그램 단일 유지.
- 실패 자동 복구·재시도 정책 변경. 기존 재시도 로직 그대로.
- 퀴즈·설문 정답의 자동 추론. 미등록이면 미시도 원칙 유지.
- 인터엠디 부활(러너 IP 403, 코드로 해결 불가).
- 세미나 종료 시각 기록(공지 값과 실제가 크게 달라 쓸모없음).

## 3. 심각도 축과 상태값 재정의

현재 상태값은 "무슨 일이 있었나" 하나의 축만 표현한다. 여기에 **심각도**를 직교 축으로 추가한다.

| 심각도 | 의미 | `actionable` 모드 |
|---|---|---|
| `ok` | 목표 달성 + 양성 증거 확인 | 전송 안 함 |
| `quiet` | 정상적인 무동작 | 전송 안 함 |
| `action` | 사람이 개입해야 함 | 전송 |
| `alert` | 고장 | 전송 |

### 상태값 → 심각도 매핑

| status | 심각도 | 비고 |
|---|---|---|
| `success` | `ok` | **`verified_by`가 있을 때만.** 없으면 `unverified`로 강등 |
| `unverified` | `alert` | 신규. 예외는 없었으나 양성 증거를 못 잡음 |
| `already_done` | `quiet` | |
| `skipped` | `quiet` | `--task` 등으로 건너뜀 |
| `no_target` | `quiet` | 신규. 처리 대상 자체가 없음(설문 대상 0건 등) |
| `not_ready` | `quiet` | 신규. 아직 때가 아님(방송 중이라 설문 미개방) |
| `closed` | `quiet` | 신규. 마감. 대상 목록에서 제거 |
| `no_answer` | `action` | 퀴즈 정답 미등록 |
| `incomplete_bank` | `action` | 설문 미등록 문항. **세미나 제목 포함** |
| `failed` | `alert` | |
| `blocked` | `alert` | 신규. 접속 차단(403 등) |

`no_questions`는 폐기하고 `not_ready` / `closed` / `already_done`로 분해한다. 현재 이 셋이 한 값에 뭉쳐 있어 "아직 안 열림"과 "고장"이 구분되지 않는다.

### 억제 대상으로 명시 확정된 것

| 현행 알림 | 새 처리 | 근거 |
|---|---|---|
| 세미나 신규 입장 성공 | `ok` → 무알림 | 사용자 요청 3.1 |
| 일일 자동화 성공 요약 | `ok` → 무알림 | 사용자 요청 3.2 |
| `⚠️ <제품명> → <시퀀스> 저장 (quiz_answers.json에 없는 제품명 — 오타 확인)` | `quiet` → 무알림 | 오타난 제품명은 퀴즈 시점에 `no_answer`(`action`)로 반드시 잡히므로 신호가 소실되지 않는다 |
| `설문 창(팝업)이 열리지 않음` | `not_ready` → 무알림 | 방송이 안 끝난 정상 상태 |
| `설문 참여 버튼이 없음` | 마감 전 `not_ready` / 마감 후 `closed` → 무알림 | §8 판정 규칙 |
| HMP 룰렛 `START 버튼이 표시되지 않음` | `quiet` → 무알림 | 미달성일이 대부분. 현재도 포맷터가 예외 처리 중 |

### 알림 레벨 스위치

CLI `--notify-level`도 받아 로컬 검증에 쓴다. 우선순위: CLI > env > 기본값 `all`.

### `actionable` 모드 메시지 형태

```

닥터빌 (승진) 퀴즈 ❓ 정답 미등록 — 우루사
  → quiz_answers.json에 우루사 정답 추가
  {"questions": [...]}          ← 오늘 문항·보기 전문

설문 ❓ 미등록 문항 2건 — "Breathe Well Symposium (호흡기)"
  → survey_answers.json 빈 값 2건
```

정상 항목은 한 줄도 넣지 않는다. 요약 헤더(`📋 일일 자동화 결과`)도 쓰지 않는다 — 문제만 오는 채널이므로 메시지 존재 자체가 신호다.

## 5. 워크플로우 재편

### 블록 구성

| 워크플로우 | 트리거 | 스텝 |
|---|---|---|
| `seminar_block.yml` (기존 `seminar_live.yml` 개명) | cron-job.org → `workflow_dispatch` | ① 인박스(11:00 런만) → ② 세미나 신청 → ③ 라이브 입장 → ④ 설문 |
| `daily.yml` | cron-job.org 15:00 KST (주) + GitHub schedule 16:00 KST (백스톱) | ① 인박스 → ② 닥터빌 출석·퀴즈 → ③ 키메디 → ④ HMP(캡슐·룰렛·댓글·글쓰기) → ⑤ 익일 퀴즈 확인 |

### cron-job.org 설정 (2개 작업)

기존 작업(`DocAuto seminar live`) 스케줄 변경:

| 필드 | 값 |
|---|---|
| Minutes | `0`, `30` |
| Hours | `11`, `12`, `13`, `14`, `17`, `18`, `19`, `20`, `21` |

→ 하루 18회. 14:30과 21:30이 포함되는데, cron-job.org의 스케줄이 분×시 교차곱이라 끝 지점만 잘라낼 수 없다. 두 런 모두 대상이 없으면 `no_target`(`quiet`)이라 무해하다.

신규 작업(`DocAuto daily`):

| 필드 | 값 |
|---|---|
| URL | `https://api.github.com/repos/SJBaek7790/DocAuto/actions/workflows/daily.yml/dispatches` |
| Minutes / Hours | `0` / `15` |

나머지 설정(메서드·헤더·body·PAT)은 기존 작업과 동일하다. **PAT은 기존 것을 재사용한다** — 같은 저장소의 Actions 권한이라 새로 발급할 필요가 없다.

### GitHub schedule 백스톱

`daily.yml`에 `schedule: '0 7 * * *'`(16:00 KST)를 남긴다.

두 트리거를 모두 두는 이유: 두 워크플로우를 모두 cron-job.org로 옮기면 **PAT 만료 하나로 전 자동화가 동시에 정지**하고, 만료는 401로 조용히 실패해 며칠간 감지되지 않는다.

백스톱이 무해한 근거: `daily_runner`는 멱등하다. 두 번째 실행은 전 항목이 `already_done`(`quiet`)이라 `actionable` 모드에서 메시지가 나가지 않는다. 15:00 런이 `no_answer`였고 그 사이 정답이 도착했다면 16:00 백스톱이 주워가는 부수 효과도 있다.

`seminar_block.yml`은 방송 시간에 묶여 있어 1시간 늦은 백스톱이 무의미하므로 외부 cron 단일 경로를 유지한다.

### 스텝 순서 근거

- **신청(②)이 입장(③)보다 앞선다.** 11:00에 개설되어 이미 방송 중인 세미나를 같은 런에서 신청→입장으로 이어 처리한다. 순서가 반대면 30분을 놓친다.
- **인박스는 11:00 런에만.** 30분마다 돌릴 필요는 없지만, 15:00 단독 폴링은 `getUpdates`의 24시간 보존 한도에 정확히 맞닿는다. 15:00 폴링 직후에 보낸 메시지는 다음 폴링까지 23시간 55분을 기다리는데, GitHub schedule 지연(최대 80분 관측 이력)이 겹치면 영구 소실된다. 11:00 폴링을 두면 최대 공백이 20시간으로 줄어 4시간 여유가 생긴다. 블록 A는 외부 cron이라 지연되지 않는다.
- **익일 퀴즈 확인(⑤)이 마지막.** 15:00에 미등재 알림이 나가면 다음 날 15:00 실행까지 24시간이 있고, 그 사이 11:00 인박스 폴링이 정답을 흡수한다.

### 세미나 신청을 30분마다 도는 비용

잡 시작 오버헤드(playwright 설치 ~2분)는 이미 도는 런에 스텝으로 얹히므로 증가하지 않는다. 늘어나는 것은 로그인 + 목록 스캔 수십 초 × 계정 수다.

## 6. 성공의 양성 증거

**규칙: `status: "success"`는 `verified_by` 필드를 동반할 때만 유효하다.** 검증부가 증거를 못 잡으면 `unverified`(`alert`)로 강등한다. `verified_by`는 사람이 읽을 수 있는 짧은 문자열(예: `"완료 팝업 #10rewardPopup"`).

| 모듈 | 양성 증거 | 현재 |
|---|---|---|
| 닥터빌 출석 | 완료 표식 재확인 | **정찰 필요(R2)** |
| 닥터빌 퀴즈 | `:text('정답입니다')` | 있음 |
| 닥터빌 세미나 신청 | 재진입 후 `a.btn_bn` 텍스트 = "신청취소" | 검증법은 알려짐, 코드 미반영 |
| 키메디 출석 | 완료 모달 "출석체크가 완료되었습니다" | 있음 |
| HMP 캡슐 | `[id="10rewardPopup"]` 출현 | 있음 |
| HMP 룰렛 | 결과 팝업 이미지 alt 파싱 성공 | 있음 |
| HMP 댓글 | alert "저장 완료" **+ 상세 재조회로 내 닉네임 확인** | 재조회 없음 |
| HMP 글쓰기 | alert 문구 + `rtn_code == 100` | 있음 |
| 세미나 입장 | 팝업 Page 획득 + 체류 후 정상 종료 | 있음 |
| 세미나 설문 | **완료 화면 문구** | 없음 — 음성 증거만 |

`already_done`도 같은 원칙을 적용한다. **"오늘 것"임을 확인할 수 없는 흔적은 완료 신호로 쓰지 않는다.** HMP 댓글의 고정 게시물 옛 댓글, 키메디의 과거 날짜 "출석완료"가 이 함정에 빠진 실제 사례다. 날짜 확인이 불가능한 곳은 `already_done` 대신 `unverified`를 반환한다.

정찰 R1이 완료 화면 문구를 찾지 못하면, 설문은 `unverified`를 반환하고 상태 파일의 `survey`를 `done`으로 기록하지 않는다. 거짓 성공으로 재시도를 영구 차단하는 것보다 낫다.

## 7. 세미나 상태 파일 스키마 v2

### 현행 (v1)

```json
{"date": "...", "accounts": {"bjh7790": {"entered": [5473], "blocks": {...}, "survey_done": [5473]}}}
```

세미나 ID만 있어 설문 알림에 제목을 쓸 수 없고, 시각 정보가 없어 마감을 판정할 수 없다.

### 신규 (v2)

```json
{
  "version": 2,
  "date": "2026-07-31",
  "accounts": {
    "bjh7790": {
      "entered": [
        {
          "id": 5473,
          "title": "Breathe Well Symposium (호흡기)",
          "start": "13:00",
          "entered_at": "2026-07-31T13:07:12+09:00"
        }
      ],
      "blocks": {"lunch": [5473], "evening": [], "manual": []},
      "survey": {"5473": "pending"}
    }
  }
}
```

- `title` — 목록 `a.list_detail` 텍스트에서 시각·진료과·연자·정원 줄을 제외한 제목 줄. 설문 알림 문구에 쓴다(사용자 요청 3.8).
- `start` — **정찰 R3 확정.** 출처는 세미나 상세의 `dd.date`이며 값 형식은 `"2026-08-10(월) 13:00 ~ 14:00"`이다. 입장 시 이미 상세 페이지를 방문하므로 추가 요청 없이 얻는다. 파싱 실패 시 `null`.
  - 목록에도 `"13:00\n~14:00"` 형태로 시각이 있지만 **날짜가 없다**(목록에 여러 날짜가 섞임). 날짜가 필요하므로 `dd.date`를 쓴다.
  - 공지 종료 시각은 상태 파일에 저장하지 않는다. 마감선 계산(§8)에만 일회성으로 쓴다.
- `entered_at` — 입장 성공 시각(KST, ISO8601). `start`가 `null`일 때 마감 판정의 대체 기준.
- `survey` — ID → `pending` | `done` | `closed`. v1의 `survey_done` 배열을 대체한다.
- 종료 시각은 기록하지 않는다(공지 값과 실제가 크게 어긋남).

### 마이그레이션

`merge_state()`가 로드 시 v1을 감지해 변환한다. `entered`의 원소가 정수면 `{"id": N, "title": null, "start": null, "entered_at": null}`로 감싸고, `survey_done` 배열의 원소는 `survey` 맵에 `"done"`으로 옮긴다. 상태 파일은 gitignore 대상이고 날짜가 바뀌면 초기화되므로, 마이그레이션은 당일 캐시 1건만 처리하면 된다.

## 8. 설문 마감 판정

### 문제

수동으로 설문을 마친 세미나가 당일 남은 모든 런에서 계속 대상으로 잡힌다. 매번 방송 팝업을 열고 버튼이 없는 것을 확인한 뒤 `no_questions`로 끝나며, 현행 알림에서는 매번 메시지가 나간다(사용자 요청 3.9).

### 규칙

마감선 = **공지 종료시각 + 1시간 30분**. 종료 시각을 못 읽으면 **`start` + 3시간**, `start`도 없으면 **`entered_at` + 3시간**.

근거(정찰 R3 실측, 12건): 세미나 길이는 60분 또는 **90분**이다(`13:00~14:00`, `17:00~18:30`, `18:30~20:00`, `12:30~13:30`). 설문 창은 종료 후 1시간이므로 종료 기준 90분 마진이면 방송이 공지보다 늦게 끝나는 오차를 흡수한다.

> 초안의 "`start` + 2시간 30분(세미나 최대 1시간 가정)"은 폐기했다. 실측 최대 길이가 90분이라 그 값은 90분 세미나에서 여유가 정확히 0이 되어, 방송이 조금만 지연돼도 설문을 놓친다. 종료 기준으로 바꾸면 세미나 길이에 따라 마감선이 자동으로 따라간다.
>
> 공지 종료 시각은 실제와 어긋난다고 확인된 값이라 상태 파일에 저장하지 않는다. 다만 어긋나는 방향이 주로 "실제가 더 늦음"이고 90분 마진이 그 오차를 덮으므로, 마감선 계산의 입력으로 쓰는 것은 안전하다.

| 관측 | 마감선 이전 | 마감선 이후 |
|---|---|---|
| `a#surveyEnter` 없음 | `not_ready` (`quiet`) — 다음 런 재시도 | `closed` (`quiet`) — `survey`를 `closed`로 확정, 대상에서 제거 |
| 설문 팝업 미개방 | `not_ready` (`quiet`) | `closed` (`quiet`) |
| 설문 창에 문항 0건 | `not_ready` (`quiet`) | `closed` (`quiet`) |

`closed`로 확정된 세미나는 그날 다시 방문하지 않는다. 사용자가 수동으로 설문을 마친 경우도 이 경로로 정리된다(마감선 전에는 재시도하지만 `quiet`라 알림이 없다).

**절충 지점:** 마감선 이전의 "이미 참여함"과 "아직 안 열림"은 구분되지 않는다. 제출 완료 후에도 `a#surveyEnter`가 사라지기 때문이다(2026-07-28 확인). 둘 다 `not_ready`로 처리되어 마감선까지 무의미한 재방문이 발생하지만, 알림이 없고 비용이 페이지 로드 한 번이라 허용한다.

## 9. 모듈 1 — 익일 퀴즈 사전 확인

**정찰 R4로 성립이 확인됐다.** 캘린더는 미래 날짜의 제품명·pId·quizId를 미리 노출한다.

### R4 실측 (2026-08-01)

| 셀 index | class | 날짜 | 제품명 | `input.pIdCls` | `input.quizIdCls` |
|---|---|---|---|---|---|
| 6 | `sat pass today` | 8/1 | 엔블로 | 141 | 3564 |
| 7 | `sun` | 8/2 | 프리스타일 리브레 | 107 | 3565 |
| 8 | — | 8/3 | 펙수클루정40mg | 108 | — |
| 9 | — | 8/4 | 우루사 | — | — |

- 오늘 포함 **4일치**가 채워져 있다(그 이후 셀은 빈 값).
- 셀 텍스트는 `"<일>\n<제품명>"` 두 줄. 오늘 셀만 class에 `today`가 붙는다.
- **`input.quizIdCls`를 새로 발견했다.** `pIdCls`(제품 식별자)와 별개인 퀴즈 자체의 식별자로, 제품명 문자열보다 안정적인 키다. 다만 현행 문제은행이 제품명을 키로 쓰므로 이번 스펙에서는 참고 정보로만 기록하고 키 전환은 하지 않는다.
- 캘린더 표기가 용량을 포함하는 경우가 있다("펙수클루정40mg"). 상세페이지 표기와 문제은행 키가 어긋나는 기존 함정과 같은 계열이므로, 등재 여부 판정은 **공백 정규화 후 부분 일치**로 한다.

### 범위 한계

문항·보기 텍스트는 퀴즈 레이어를 열어야 나오고, 레이어를 미리 여는 것은 하루 3회 제출 기회를 소모할 위험이 있다. 따라서 이 모듈이 낼 수 있는 산출물은 **제품명과 문제은행 등재 여부**까지다. 문항을 미리 받아 정답을 준비하는 시나리오는 성립하지 않는다.

### 동작

`daily.yml` 마지막 스텝. `/product/main` 캘린더에서 내일 셀의 제품명을 읽고:

| 조건 | status | 심각도 |
|---|---|---|
| `quiz_answers.json` 또는 `quiz_answers_legacy.json`에 제품명 존재 | `already_done` | `quiet` |
| 양쪽에 없음 | `no_answer` | `action` — "내일 퀴즈: X — 정답 없음" |
| 내일 셀이 비었거나 "?" | `not_ready` | `quiet` |

등재돼 있어도 그 제품의 **오늘 문항**이 은행에 있으리라는 보장은 없다(같은 제품이라도 날짜마다 문항이 다름). 이 알림은 "정답을 준비할 시간이 있다"는 예고이지 다음 날 성공을 보장하지 않는다.

`credentials.json`의 구조는 이미 계정 키 최상위 + 사이트 하위이고, 각 스크립트가 `--account`로 `data[account][site]`를 읽는다. **스키마 변경은 불필요하다.** 문제는 코드에 박힌 계정 목록이다:

| 위치 | 하드코딩 |

## 12. Acceptance criteria

### A. 알림 게이트
1. `scripts/notify.py`가 `severity_of` / `should_send` / `build_message` / `send_telegram`을 제공하고, 앞 세 함수는 순수 함수로 단위 테스트된다.
2. `NOTIFY_LEVEL` 미설정 시 `all`로 동작해 현행과 동일한 전체 요약을 보낸다.
3. `NOTIFY_LEVEL=actionable`에서, 모든 노드가 `ok`/`quiet`면 **텔레그램 API 호출 자체가 발생하지 않는다**.
4. `NOTIFY_LEVEL=actionable`에서 `action`/`alert` 노드가 있으면 그 노드만 담은 메시지를 보낸다. 정상 노드는 포함되지 않는다.
5. `daily_runner`·`seminar_block`·`seminar_survey`가 모두 `notify.py`를 통해서만 전송한다. 각 스크립트에 남은 개별 전송·판정 로직(`seminar_live.should_notify` 포함)은 제거된다.
6. 인박스의 "문제은행에 없는 제품명" 경고는 `quiet`로 분류되어 `actionable`에서 전송되지 않는다. 저장 동작 자체는 현행 유지.

### B. 성공 검증
7. §6 표의 모든 모듈이 성공 시 `verified_by` 문자열을 결과 JSON에 포함한다.
8. 양성 증거를 못 잡으면 `success`가 아니라 `unverified`를 반환하고, `unverified`는 `alert`로 분류된다.
9. `seminar_survey`는 완료 화면 확인(R1) 없이 `success`를 반환하지 않으며, `unverified`인 세미나를 `survey`에 `done`으로 기록하지 않는다.
10. HMP 댓글은 저장 alert 확인 후 **상세를 재조회해** 내 닉네임이 있는지 확인하고, 확인되면 `verified_by`에 그 사실을 남긴다.
11. 닥터빌 세미나 신청은 신청 후 상세를 재진입해 `a.btn_bn` 텍스트가 "신청취소"임을 확인한다.
12. 날짜를 확인할 수 없는 흔적으로는 `already_done`을 반환하지 않는다.

### C. 워크플로우
13. `seminar_live.yml`이 `seminar_block.yml`로 개명되고, 스텝 순서가 인박스(11:00만) → 세미나 신청 → 입장 → 설문이다.
14. 인박스 스텝은 KST 시각이 11시일 때만 실행된다.
15. `daily.yml`이 `workflow_dispatch`(주 트리거)와 `schedule: '0 7 * * *'`(백스톱)을 모두 가지며, 스텝 순서가 인박스 → 닥터빌 → 키메디 → HMP → 익일 퀴즈다.
16. 두 워크플로우 모두 `NOTIFY_LEVEL`을 env로 주입한다.
17. cron-job.org 설정값(시간표·신규 작업)이 `MEMORY.md`에 반영된다.

### D. 상태 파일·설문 마감
18. 상태 파일이 v2 스키마로 저장되고, v1 파일을 로드하면 자동 변환된다(단위 테스트 포함).
19. 입장 성공 시 `title`·`start`·`entered_at`이 기록된다. `start`는 상세 `dd.date`를 파싱해 얻고, 파싱 실패 시에만 `null`이다.
20. `incomplete_bank` 알림에 **세미나 제목**이 포함된다.
21. 마감선(§8: 공지 종료시각 + 1시간 30분, 폴백 `start`/`entered_at` + 3시간) 이전의 설문 미개방은 `not_ready`, 이후는 `closed`로 판정되고, `closed`는 당일 재방문 대상에서 제외된다(단위 테스트 포함).
22. `dd.date` 파서(`"2026-08-10(월) 13:00 ~ 14:00"` → 시작·종료 datetime)가 순수 함수로 분리되어 단위 테스트된다.

### E. 계정 확장성
23. `common.list_accounts(creds, site)`가 사이트 블록 보유 계정만 반환하고, `daily_runner`·`seminar_block`·`seminar_survey`가 하드코딩 목록 대신 이 함수를 쓴다.
24. `credentials.json`에 계정을 하나 추가하면 코드·워크플로우 수정 없이 해당 사이트 작업이 실행된다(단위 테스트로 검증).

### F. 정찰
25. `scripts/recon.py --item R3|R4`가 구조화 JSON + 스크린샷을 `scripts/logs/`에 남긴다.
26. `RECON=1`일 때만 R1·R2 계측이 동작하고, 기본 실행에는 영향이 없다.
27. 정찰 산출물은 artifact로만 업로드되며 git에 커밋되지 않는다.

### G. 공통
28. 기존 `python3 -m pytest`가 전부 통과한다.
29. `CLAUDE.md`(200줄 이하 유지)와 `MEMORY.md`가 갱신된다.

## 13. 리스크

1. **`unverified` 폭증.** 검증을 조인 직후 며칠간은 양성 증거를 못 잡는 모듈이 알림을 쏟을 수 있다. 첫 1달은 `NOTIFY_LEVEL=all`이라 어차피 전량 수신하므로, 이 기간에 증거 셀렉터를 다듬는다.
2. **설문 완료 화면을 못 찾을 위험(R1).** 그 경우 설문은 영구히 `unverified`가 되어 매번 알림이 온다. 차선책은 제출 직후 방송 팝업을 재방문해 `a#surveyEnter` 소실을 확인하는 것이지만, 마감과 구분되지 않아 약한 증거다. R1 실패 시 이 차선책을 쓸지 재논의한다.
3. **PAT 단일 실패점.** `daily.yml` 백스톱이 일일 루틴은 지키지만 세미나 블록은 못 지킨다. PAT 만료일 캘린더 등록과 cron-job.org 실패 알림이 여전히 필수다.
4. **무알림의 근본 위험.** 워크플로우가 아예 실행되지 않으면(외부 cron 정지, 저장소 정지) 알림이 안 오는 것과 정상이 구분되지 않는다. 이번 스펙은 이를 다루지 않는다. 필요해지면 주 1회 하트비트를 별도로 논의한다.
5. **마감선 2시간 30분의 근거는 관측이 아니라 추정이다.** 실제로 설문 창이 더 길게 열려 있으면 `closed`로 조기 확정해 설문을 놓친다. 첫 1달 전량 알림 기간에 실측으로 조정한다.

## 14. 채택하지 않은 대안

- **모듈별 알림 판정(각 스크립트가 `notify` 플래그를 붙임).** 정책이 5곳에 흩어져 "왜 안 왔는지" 추적에 5곳을 봐야 한다. 현행 `should_notify`가 이미 이 방식이고 실제로 다른 스크립트와 규칙이 어긋나 있다.
- **날짜 기반 자동 알림 전환.** 전환일을 코드에 박으면 그날 이후 더 보고 싶을 때 커밋이 필요하다. repo variable이 즉시 양방향이다.
- **두 워크플로우 모두 외부 cron 단일화.** PAT 만료 시 전 자동화 동시 정지. 백스톱 유지 비용이 사실상 0이라 굳이 없앨 이유가 없다.
- **세미나 종료 시각 기록.** 공지 값과 실제가 크게 달라 마감 판정에 쓸 수 없다(사용자 확인).
- **설문 대상에서 "버튼 없음 2회 연속 관측 시 마감" 판정.** 방송 중이라 아직 안 열린 상태에서 두 번 관측되면 진짜 설문을 놓친다. 시간 기준이 안전하다.
